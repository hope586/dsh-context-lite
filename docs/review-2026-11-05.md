# 代码审查与修复记录（2026-11-05）

本轮对当前源码（基于 0.3.2，含未提交的 Desktop 0.2.2-rc.1 启动兼容修复）做了一次以真实影响为筛选标准的审查与修复，覆盖两条主线：(1) bug、兼容与鲁棒性；(2) 性能、架构与用户可见表现。所有修改仅位于当前工作区，未提交、未发布、未改动任何宿主安装镜像或配置。

**修订（第二轮，主控复核后）**：第一轮改动引入了两处新问题，主控独立复现其中一处阻断回归并指出另一处风险，本轮均已处理：

1. **主控发现并已修复的回归（第一轮引入，未随任何发布交付）**：`buildAudit` 的回合记录索引 `roundRecords` 存的是 seq 数字，但快照的 identities 循环把它当作记录对象直接传给 `pluginNode`，`n.type` 恒为 undefined——本轮内注入后又被替换的插件内容（transient）从 `changes` 中完全消失。主控用最小 fixture（PluginA append → PluginB replace → assistant → turn/end）复现：基线含 PluginA `transient:[1]`，候选完全丢失。修复为在消费点把 seq 映射回 `records.get(seq)` 记录对象。新增 4 项回归（同轮单次替换、链式替换、同源重入、跨轮 removed），在损坏中间版上失败、修复后通过；并扩展差分验证到含插件替换/transient 的 fixture（见下）。
2. **撤回第一轮的消息指纹记忆化（collector.js）**：按对象身份用 WeakMap 缓存 `messageStamp` 依赖"消息对象深不可变"，但插件传入/返回的消息对象没有宿主层面的深冻结保证。构造的真实危害场景（在记忆化版本上实测失败）：(a) 中间件对 baseline 中同一对象就地改写 content——原实现按指纹变化归因给改写方，缓存版本沿用旧哈希判定"未变化"而丢失归因；(b) 同一对象跨轮复用并修改——第二轮沿用第一轮哈希，接纳匹配失败、归因丢失。宿主 `Session.append` 会在接纳点做 JSON 快照与深冻结，接纳事件对象与生产者对象天然不同，该优化收益有限而风险真实，已完整撤回。新增 3 项回归锁定指纹语义（就地改写归因、跨轮复用新鲜指纹、决策后修改必须破坏身份匹配而非错误归因）。

## 确认并修复的问题（原仓库既有缺陷）

### 1. 长会话重建的二次方 CPU 与内存（`src/audit.js`）

- **触发条件**：会话轮次多、保留节点多（例如数百轮、数千事件）时任何一次读取——侧栏刷新或开发者接口都会整段重放。
- **根因**：`snapshot()` 在每条 `assistant/message`（每个逻辑请求）和每个回合结束时重新执行 `surface.nodes.map`，为**每个保留节点**重新 `deriveEventMessage`、`estimateMessage` 并展开一个新节点对象；各回合与请求各自持有这些副本。
- **影响**：800 轮（约 7200 事件、1600+ 逻辑请求）合成会话上，`buildAudit` 约 1.7 s，审计图保留约 1.1 GB（第一轮临时脚本实测 heap 1.19 GB）。
- **修复**：节点视图与 token 估算按 seq 记忆化并在全部快照间共享；工具定义估算按 header seq 记忆化；回合内记录走增量索引（`roundRecords`，消费点映射回记录对象）；`changes` 的 identities 计算不再每次全量过滤 `records`。
- **验证**：旧/新实现在含插件同轮替换/transient、链式替换、同源重入、压缩、中断、attempt、工具回合、轮间更新的 1/2/3/17/60 轮 fixture 上对 `rounds`（含 `changes`）、`requests`、`current`、`records`、逐回合逐片段 `readDetail` 输出**完全一致**；开发者 v1 快照/差异/导出**字节级一致**。新增守卫测试用独立 `SurfaceManager` 重放核对每轮 total。

### 2. 侧栏概览负载重复携带整份节点对象（用户可见）

- **触发条件**：打开侧栏的会话随每次会话事件刷新（投影 revision 变化，80 ms 去抖后取整份概览）。
- **根因**：`overview()` 把每个可见回合每个片段的 `refs` 逐一展开为带 provenance 的完整节点副本；历史/工作片段随会话线性增长，可见回合窗口内总量为平方级。
- **影响**：合成会话 200 轮约 33–36 MB/次、800 轮约 175 MB/次（较轻 fixture），序列化最高 0.58 s；实际使用中体现为长会话侧栏刷新变慢、网络与渲染开销随会话长度恶化。
- **修复**：wire 上 `refs` 只保留 `{seq}`；超过 48 条时改为单一 `refCount`；悬停提示的日志列表最多显示 12 个 seq 加省略号，长片段显示条数。客户端与文案同步更新（`refsTruncated` 中英文）。
- **验证**：新增回归断言负载上限与字段形状（30 轮 fixture 约 1.06 MB → 阈值内，基线失败）；`test/client-wire.test.mjs` 基于真实构建产物验证长 refs 分页、悬停文案与合并语义；逐点核对客户端全部 `refs` 访问与 `refCount` 兼容。

### 3. 逻辑请求详情原样返回无界节点副本（`src/index.js`）

- **触发条件**：展开某轮的请求详情（`kind=request`）。
- **根因**：路由直接返回 `req`，其中 `inputSegments[].refs` 为当时全部保留节点的完整副本（含 provenance），长会话中单个历史片段可达数千条。
- **修复**：与概览同一 `slimSegment` 精简（`{seq}` / `refCount`）；客户端对截断显示"另有 N 条"。
- **验证**：回归测试（60 条消息合并片段 → `refCount`，无 `refs`）；旧代码失败。

### 4. 只读路径在元数据存储中创建空会话行，可逐出真实证据（`src/origin-store.js`）

- **触发条件**：读取（侧栏或开发者接口）从未产生过归因记录的会话；`originFor` 每个事件、`inspect` 每次读取都会走"取或建"语义的 `session(id)`。
- **根因**：读路径也会插入空行并参与 LRU 逐出；内存模式（无宿主存储表）下被逐出的行不可恢复。
- **影响**：批量查看无记录会话可把有真实归因的会话挤出 64 会话窗口，归因丢失且界面显示"来源方未记录"；有存储时也会造成无谓的逐出/重水化。
- **修复**：新增 `peek()`——命中缓存或存储表才返回，读路径不再创建行；写路径行为不变。
- **验证**：回归测试（`maxSessions=2`，记录 1 个真实会话后读 5 个未知会话）：旧代码真实归因被逐出（失败），新代码归因完好且不占会话名额。

### 5. 元数据热路径的逐次全量 actor 清理（`src/origin-store.js`）

- **根因**：`record()` 每次调用 `pruneActors`，扫描全部保留 events+evidence（各至多 2000 条），采集侧每次接纳都支付 O(保留量)。
- **修复**：仅在发生裁剪、同 seq 覆写或 actor 数超 guard（128）时清理——未使用 actor 只可能由这两种变化产生，不变量保持。
- **验证**：可复现基准中 4000 次 `record`（3 会话、2000 条窗口）从约 183 ms 降至约 26 ms；既有存储/裁剪/actor 版本测试全部通过。

### 6. 同一消息沿接纳路径重复全文指纹（`src/collector.js`）——优化已撤回

第一轮曾按对象身份用 WeakMap 记忆化成功的 `messageStamp`（8.7 KB 消息 600 次接纳 0.118 → 0.068 ms/条）。主控指出该假设不成立；实测确认两处真实危害（见文首修订 2）后**完整撤回**，保留原有"每次观察重新计算指纹"的行为，并新增 `test/admission-mutation.test.mjs` 三项回归锁定可变对象语义。采集热路径的剩余改善全部来自问题 5 的存储摊销（基准：103.5 → 87.2 µs/条，含接纳写入）。

## 剩余风险（有证据或明确边界，未强行修改）

1. **整段重放仍为 O(会话长度 × 逻辑请求数)**：800 轮重建约 1 s，每次读取（游标变化后）重新发生。增量审计属架构级改动，本轮未做；快照内记忆化已消除重复派生与定价，剩余为分组循环本身。
2. **重建缓存上限（默认 4 会话）× 长会话审计图**：极端情况下可驻留数百 MB，属配置边界（`maxCachedSessions` 1–32）。
3. **前端时间线未虚拟化**：每次刷新仍重渲染全部可见回合（≤120）；悬停提示不再触发超大字符串，但 DOM 规模不变。展开回合时"来源变化"会为每个历史 seq 渲染按钮，长保留插件来源可达数百个——基线既有行为，未改。
4. **概览合并的回合间隙**：复核确认自动刷新合并不会移动首个显示回合，`hiddenRounds` 计数因此保持正确（已抽取 `mergeOverview` 纯函数并用回归锁定，行为与基线一致）；真正的限制是当服务端窗口跳过中间轮次时，合并列表不连续且间隙轮次无法通过"更早回合"取回——基线既有行为，修复需要新的取数逻辑，未动。
5. **同一根 events 上并存两个观察器实例**（插件重载竞态）会嵌套包装监听器；正常流程 Cordis 先卸载旧 fiber，未加跨实例去重。
6. **元数据写失败不重试**（`ORIGIN_STORAGE_ERROR` 已上报）、**会话清单扫描 4096 上限**、**注销翻译假设 hooks 数组身份稳定**：均为基线既有边界，行为未变。
7. **未实测项**：本轮未重启或连接实际 Desktop/Web 宿主，事件兼容结论基于锁定的开发依赖 Cordis 4.0.5 与既有 0.3.2 专项记录；`DSH_TEST_CORDIS_URL` 指向新版宿主 Cordis 的复测因可导入模块不在只读范围内而未执行。性能数字为合成 fixture 的计算测量，不代表端到端延迟。
